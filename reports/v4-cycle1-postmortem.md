## 1. 結論（先に読むこと）

**Cycle 1 の高速化は「速度は改善したが、正当性の根拠が崩れている」状態である。
commit `3bed458` のまま残すべきではない。**

| 項目 | 実測 |
|---|---|
| 速度（prism7） | 8.69s → 2.85s（**3.05x**）— 実在する |
| 速度（stairs） | 59.3s → 31.2s（1.90x）— 実在する |
| テスト | 265 passed |
| 一意数の既知値 | 11 / 54 / 99 / 354 / 1516 / 1290 / 5714 すべて一致 |
| **既存プリセット外の入力での正当性** | **未検証。かつ理屈が破綻している（§3）** |

「テストが通る」「既知の一意数が合う」だけでは**_this optimization is correct_ を
主張できなかった**。Cycle 2 の圧縮改造で同じコードが 305 に壊れたことで、
その疑いが裏付けられた。

---

## 2. 何をやろうとしたか

`fifth.py` の `iter_unique_nets` は全域木ごとに `_net_signature` を呼び、
その中で `_wl_refine`（1-WL 色細分）を Python のループで回していた。
prism7 のプロファイルでは全体の **約77%** がここを占め、
`hash()` の呼び出しが 2,600 万回発生していた（`reports/` 内の実測）。

方針: 色細分は木ごとに独立なので、**窓（2048木）単位でまとめて numpy に流す**。

---

## 3. 破綻した理屈（最も重要な発見）

### 3.1 当初以为是問題なかった理由

色細分は「**色数（distinct count）が初めて増えなくなったラウンド**」で停止する。
これは同型な木なら同じラウンドで止まると思った。

**それは間違いだった。**

実測（`tools/repro_freeze.py`, cube 384木）:

```
最初に全42... 全24色に到達するラウンドの分布:
  round 6:  96 trees
  round 7: 168 trees
  round 9:  24 trees

同型クラスの中で凍結ラウンドがばらつく組: 4/11
  → rounds=[6, 7] size=48
```

**分割（partition）は同じなのに、「色数が止まるラウンド」が木ごとに違う。**

### 3.2 なぜこれがキーの一致を壊すか

各ラウンドでラベルは

```
h ← A*h[i] + B*h[nxt] + C*h[partner] + tag      (mod 2^64)
```

と**毎回作り直される**。分割が安定していても、ラベルの**値**は変わる。

キーは `tuple(sorted(colors))` なので、

- 分割が同じ = キーの**要素の集合**は同じ
- 凍結ラウンドが違う = キーの**値**が違う
- → **同型な木が別々のキーになる（過分割）**

これは理屈の限界ではなく**実装の欠陥**であり、
「回数を/initials で決める性質」を使うべきだった。

### 3.3 なぜCycle 1のテストが通ったのか

過分割は**個別化フォールバックで相殺されていた**。

- prism7: 35,287木のうち **34,776木（98.6%）が全42色まで細分される** → プレーン経路
- 残り 511木 → `_individualize_refine`（Python の完全同型判定）に回る

プレーン経路が過分割しても、個別化経路が正しい値を出すため、
**合計で見ると正しい件数が observers fortuitously 出ていた**。

ただしこれは保証ではない。過分割が Salt 少ない立体（個化が必要な木が
プレーン経路の過分割をちょうど相殺する組合せ）では崩れる。
实际上、Cycle 2 の圧縮改造により cube が 11 → 305 に崩れた（§4）。

---

## 4. Cycle 2 で実際に起きたこと（圧縮の改造）

行を間引く（安定した行を計算から外す）改造を入れて再計測したところ:

```
cube     11 → 305
prism6  354 → 3382
```

原因を潰しながら 2 つのバグarka 見つけた:

1. **`h = h[keep]` が古い色を保持していた**
   圧縮時に「新しい色」ではなく「前のラウンドの色」を残していたため、
   `counts` だけが新しくなり次のラウンドで必ず「変化なし」と判定され、
   1〜2 ラウンドで全行が停止 → 全行が個別化経路に落ちる。

2. **`if keep.all(): return` が反転条件だった**
   `keep.all()` は「未安定の行がまだある」= **続行すべき**状態。

この2つを直すと、プレーン経路が本当に全色まで到達するようになり、
**§3 の凍結ラウンド差が顕在化した**（305）。

## 6. 今後の方針（この報告を書き上げる時点で確定している事実）

- 速度改善（3x）は**実在する**。batch 化の考え方自体は正しい。
- ただし **キー生成の正しさは未修正**。凍結ラウンド依存を排除する必要がある。
- 候補:
  - (a) 全行を**同���ラウンド数**まで回す（最も遅い行に合わせる）。
    単純で slowest-row が窓の速度を支配するが、多項式ハッシュなので
    値がごとに変わるため「追加ラウンドで値が壊れる」危険は無い。
    **これが最も単純で安全な修正**。
  - (b) ラベル値をラウンド非依存にする（例: 最終分割を正準ラ_sorted-符号化）。
    計算量は増えるが速度は落ちる。
- いずれにせよ、**検証は「既知の一意数」だけでなく
  「木ごと版の `_net_signature` と1木ずつ突き合わせて一致すること」**を
  機械的に回す形にしないと、同じ過分割を再発する。
