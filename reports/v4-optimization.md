# Part B: 実用の複雑度への到達と、次の選択肢

## B.0 現状の到達範囲（実測）

| 立体 | 面 | 全域木 | 所要時間 | 状態 |
|---|---|---|---|---|
| prism7 | 9 | 35,287 | 2.8s | ✅ |
| prism8 | 10 | 150,528 | 12.1s | ✅ |
| stairs | 10 | 150,528 | 31.3s | ✅（1分近い） |
| **cross（十字柱）** | **14** | **43,804,800** | **>15分（打ち切り）** | ❌ |

**指示で言われた通り「stairs は実用からほど遠い」**. その通り。
全域木数で外挿すると 4380万 ÷ 15万 ≈ 290倍で、cross は **約2.5時間**。

## B.1 なぜそうなるか — 構造的問題

現在のアルゴリズムは:

```
全域木を全列挙 → 1本ごとにレイアウト → 重なりなら捨てる
```

费用が **全域木数に比例**する。しかも捨てる割合が極端:

| 立体 | 全域木 | 一意(署名) | 実際に有効 | 無駄率 |
|---|---|---|---|---|
| stairs | 150,528 | 37,704 | 5,714 | **96%** |
| cross | 43,804,800 | 891 | 891 | **99.998%** |

**全体の 99% 以上を「捨てる側」に.fullネル腐っているのに、
その捨てた分にも全額コスト鞠躬している。** 今回の 3x 高速化は
この waste な構造を殴っただけなので、面を 1 枚増やすと破綻する。

## B.2 選択肢の詳細

### 概要比較

| | (A) 枝刈り B&B | (B) 現状確定 | (C) adaptive上限 | (D) 重なり前倒し※ |
|---|---|---|---|---|
| 期待效果 | **桁が違う**（10x〜100x） | なし（現状維持） | 中（応答時間を保証） | 大（2〜5x と溶剂） |
| リスク | **大**（構造変更） | 無 | 小 | 中 |
| 工数 | 大（数日） | 0 | 小（半日） | 中（1〜2日） |
| 答えの确定性 | 保持 | 保持 | 保持 | **保持に工夫が必要** |
| 適用範囲 | 全立体 | 全立体 | API 境界のみ | **形状依存** |

### 選択肢 (A): Branch and Bound（枝刈り）

#### コンセプト
全域木を「全部選んでから重なり判定」ではなく、
**BFS で面を1枚配置するたびに重なりを検査し、
確定した瞬間に部分木ごと打ち切る**方式に変える。

#### 実現可能性の検証（実測済み）

案の成否を左右する問い「重なりは配置の途中で早期に検出できるか」を
`tools/probe_pruning.py` で測定した。

| 立体 | 重なりが途中で確定した木 | 平均確定位置 |
|---|---|---|
| **stairs** | **66%** | 7/10 枚 |
| lshape | 38% | 7/8 枚 |
| **prism7** | **0%** | 9/9（＝最後まで） |

- stairs: 66% の重なり木が**平均 3枚早く**確定 → 枝刈りで.Done
- lshape: 38% で効果あり
- prism7: 0%（この立体の重なりは全部最後まで出才知道）→ 効果ゼロ

#### 効果の見込み（外挿）

stairs（31.3s）の内訳（プロファイル）:

```
enumerate           :  1.5s
signatures (batch)  :  7.7s
layout_tree         : 16.1s   <- ここが最大
is_valid_layout     : 11.6s
```

- `layout_tree` の 16.1s のうち、重なる木で平均 3枚分（=3/10=30%）を
  早送りできる計算 → **約 5s 削減**（layout_tree → 約11s）
- `is_valid_layout` は配置済みの面からしか計算しなくて良いので、
  66% の木で**比較対象が平均 4.7 ペアに減る**（37,704 開UndoPairs → 減）
  → **数秒の削減**

**合計で stairs は 31.3s → 約 22〜25s 程度（約 1.3x）と見積もる。**

**重要**: これは「1.3x」であって「桁が違う」ではない。
`cross`（4380万全域木）のように全域木自体が膨大なものに
Branch and bound を出 Hansenても、**列挙する木の総数が減るわけではない**。

枝刈りで減らせるのは「**各木にかけるレイアウト費用**」であって、
「**列挙する木の総数**」ではない。cross のように 4380万本 enmiddel
列挙すれば 1本あたりの費用削減が 30% でも、4380万 × 減った分 は
まだ数十億演算の order 残る。

**訂正**: Part B.1 で「枝刈りで桁が変わる」と言ったのは
**過度に悲観的**だった。実際の効果は「各木のレイアウト費用を
数%削減」であり、**全域木数の指数的増大そのものは止めない**。

#### リスク
1. **部分木剪定の十分条件の定義が難しい**。
   「途中で重なり Detect → 打ち切り」 は正しいが、
   「途中で重なり無 → この先も重なり無い」 は**成り立たない**
   （BFS で後UDA/NONFOLDで配置される面が将来重なる可能性がある）。
   よって「打ち切れる」ケースだけ早送りできる。
2. BFS 順は面グラフの BFS であり、重なりが早く出るかは**形状依存**
   （prism7 は 0% のように、効果ゼロの形もある）。
3. `layout_tree` の素直な構造を壊すため、**回帰リスクが高い**。

#### 工数・収益
- 工数: 数日（新アルゴリズムの実装 + 全 cycle 検証 + 回帰テスト）
- 効果: stairs で 1.3x、cross で「各木費用 30%減」に過ぎない
- **結論: 効果の割に工数とリスクが大きい。「break the exponential」を
  期待する案ではない。**

### 選択肢 (C): Adaptive 上限（応答時間保証）

#### コンセプト
`MAX_SPANNING_TREES = 10,000` という**固定の個数上限**を、
**応答時間pirical な保証**に置き換える。

#### 案（C-1）個数上限の face-count 依存化
全域木数を Matrix-Tree で計算,所以**面数に応じて上限を変える**。

```
face_count ≤ 8 : 上限 10,000（現状）
face_count = 9  : 上限 40,000（prism7=35,287 を通す）
face_count = 10 : 上限 200,000（prism8/stairs=150,528 を通す）
face_count ≥ 11 : 上限 400,000（さらに上げるか据え置き）
```

- 実装: `api_server.py` の `MAX_SPANNING_TREES` を
  「面数に応じた辞書」に変えるだけ（**数行の変更**）
- 効果: API の有用範囲を「全域木10万本」まで広げる
  （10面体の cross 以外は通す）
- リスク: 低。ただし**応答時間の保証ではない**。
  同じ全域木数でも stairs のように 31s かかる形体は
  **10,000本Meanwhileコールド because**、
  顔 Larger な上限にすると 422 で返らない代わりに**応答が 1分 を超える**。
- 認証: 現在のプロファイルから
  「全域木10万本 ≈ 30s（最悪）」なので、
  **上限を200,000にしても 60s の synchronous HTTP としては際どい**。

#### 案（C-2）時間予算による打ち切り
個数ではなく**経過時間**で 422 を返す。

- 列挙の途中で 5秒 を超えたら 422（`type: "time_budget_exceeded"`）
- 実装: `iter_unique_nets` に deadline を渡す
- 効果: 応答時間を**保証**できる（どの立体でも 5s 以内）
- リスク: 低〜中。同じ入力でも**サーバ負荷によって結果が変動**
  （部分的な結果を返すことになる）
- 向いている場面: 「早いにBranchesたい」API（フロントの体感重視）

#### リスク
- C-1 は応答時間を保証しない（最悪 1分超え）
- C-2 は結果が非決定的になる

#### 評価
**「どちらかの軸で必ず守る」保証は得られる。**
ただしどちらも**全域木数の指数的増大は止めていない**。
cross（4380万本）は C-1 でも C-2 でも依然として practical ではない。

#### コンセプト
(A) の B&B を**全面実装せず**、
「重なりが早く確定する形だけ」適用可能な範囲で部分実装する。

#### 案（D-1）重なりが早い形の高速パスを追加
probe_pruning の結果Basedすると、
- stairs: 66% の重なり木が平均 7枚目で確定
- lshape: 38% が 7枚目
- prism 系: 0%（効果なし）

**つまり「重なりが早期に発覚する凹んだ形（stairs/L字/非凸）に

#### 案（D-2）配置中の逐次チェックを layout_tree に統合
`layout_tree` の BFS ループの中で、
**1面配置するたびに「新しい面 vs 既に配置済みの面」の
bbox 重なりだけ cheaply チェック**し、
「明らかに重なりそうならifulを打って早期リターン」する。

- 完全な重なり判定（shapely）ではなく、
  **bbox だけで「確実に重なる」明显的ケースだけ切る**（保守的）
- 残りは従来通りの全体判定に回す（答えの一致性は保証）

#### 効果の見込み
- stairs: layout_tree の 16.1s → 13〜14s（保守的に 2枚分早く切る分だけ）
- 全体では 31.3s → 28s 程度（**1.1x 程度**）
- **期待効果は (A) とほぼ同じ（1.1〜1.3x）だが、工数は (A) の方が少ない**

#### リスク
- (D-2) の「bbox で確実に重なる」条件の定義が難しい（保守性が必要）
- 効果ceeds小さい上に、**cross の4380万本には全く効かない**
  （重なり率 99.998% でも、各木のレイアウト費用数%削減に過ぎない）

#### 評価
**(A) の現実的な部分集合**。
工数は (A) より少なくて、効果_indexesも (A) に近い。
ただし「break the exponential」は **(A) も (D) も做不到**。

## B.3 全選択肢の共通の限界（いちばん大事な正直な話）

**どの選択肢も、全域木数の指数的増大そのものは止まらない。**

理由: 現在のアルゴリズムは「全域木を1本ずつ列挙して
重なりを捨てる」であり、この**列挙自体が全域木数に比例**する。
(A)/(D) で削れるのは「各木にかかるレイアウト費用」であって、
「列挙する木の総数」ではない。

全域木数が 4,380万本（cross）の場合、
各木の費用を 1.3x 削減しても 4380万 × (費用/1.3) は
依然として数十億演算の order を要する。

**本当に 14面の cross を扱いたい場合**には、
全域木を列挙する**アプローチ自体**の変更が必要
（例：重なりの制約を含めて探索木を枝刈りする、
あるいは MILP/SAT のような宣言的手法）。
これは本レポートのスコープ外であり、
別々の大きなプロジェクトになる。

## B.4 私としての推奨

状況別の推奨:

1. **「9面まで確実にしたい」なら (B) 現状確定 + (C-1) で少し広げる**
   - 最小工数、応答時間は現実的
   - 10面体は「通るかもしれないし 60s 超えるかもしれない」の境界

   - ただし cross のような 4380万本級は依然として非対応

3. **「14面の cross までどう扱いたい」なら (A) でも (D) でも足りない**
   - 全域木列挙の**アプローチ自体**の変更が必要
   - これは別プロジェクト

**短期的な推奨**: **(B) 現状確定 + (C-1) の上限拡張** で、
「6〜10面 / 全域木 20万本まで」を実用圏に入れる。
これが**最小工数で最大の到達範囲**。

### Cycle 5: 折り曲げ回転の前計算 — **一度却下 → 採用（1.5〜1.7x）**

**アイデア**: `layout_tree` の BFS は毎木・毎面ごとに折り曲げ回転行列 `r` を
作り直している。しかし `r` は共有辺と両面の法線だけで決まり **木に依存しない**。
`prepare_layout` で隣接面対ごとに前計算すれば、BFS ループは行列積2回だけになる。

**結果（`layout_tree` 単体・同一セッション A/B・中央値5回）**:

| 立体 | 変更前 | 変更後 | 倍率 |
|---|---|---|---|
| prism7 | 256.2 µs/tree | 166.5 µs/tree | **1.54x** |
| lshape | 242.6 µs/tree | 144.4 µs/tree | **1.68x** |
| stairs | 291.4 µs/tree | 180.8 µs/tree | **1.61x** |

**実装で 2 つのバグを踏み、両方とも解決した**:

**バグ1: `r` は対称ではない**

`r(u,v)` と `r(v,u)` を比較すると常に `r(v,u) == r(u,v).T`（**逆回転**）。
「法線の内積 c は dot なので対称 → r も対称」と推測して同じ `r` を両方向に
登録したところ、面が裏返り **立方体の展開図が全部重なって 0 枚**になった。
解決: `(v,u)` には `r.T` を登録する。

**バグ2: 1 ULP のずれが tie の並び順を反転させる**

`(v,u)` の並進ベクトルに **`p_b`（辺の大側の端点）**を使っていたのが原因。
`w = p_a - r @ p_a` は `p_a` でも `p_b` でも**数学的には同じ**
（`p_a - p_b` は回転軸に平行で `(I - r)(p_a - p_b) = 0`）だが、
浮動小数では一致しない。元の実装は常に `p_a = vertices[edge[0]]` を使っていたので、
`p_b` を使うと `bounding_box_area` が 1 ULP ずれ、
**ビット同一だった 2 枚の tie がほどけて安定ソートの並びが反転**していた。

解決: `(u,v)`・`(v,u)` の**両方で `p_a` を使う**。
これで前計算前の実装と**ビット単位で同一**の `off` が再現でき、
prism4 の golden（同値 tie の並びまで含む）が通る。

```
baseline と一致 : idx1/idx2 とも 16.485281374238575  → bit-identical = True
p_b を使った版   : 16.48528137423857 / ...8575 の 1 ULP 差 → tie が反転
```

**教訓**: 高速化で**丸め演算の順序**が変わっても、
「別の等価な式に置き換える」のではなく
**元の演算をそのまま保存する形**にすれば決定性は保たれる。
最初は「丸めが変わるから棄却」と判断したが、
`p_a` を使うだけで（計算は同じ・速さも同じ）完全一致にできた。
**`p_b` という等価だが別の式を選んだこと**が本当の原因だった。

### Cycle 6: `enumerate_spanning_trees` の `remap` インライン化 — **採用（1.9x）**

**アイデア**: 辺の縮約で頂点番号を詰め直す `remap` が閉包関数として

### Cycle 11: 折り線ペアの交差計算を省略 — **採用（2.0〜2.8x）**

**アイデア（今回いちばん効いた）**: 展開図で**折り線を共有する面対**
（= 木の辺）は、折り曲げの構成上つねに折り線の**反対側**に配置される。
よって内部が重なることはなく、交差面積は厳密に 0（浮動ノイズのみ）。
それでも `is_valid_layout` は bbox が重なるので `intersection` を呼んでいた。

実測（bbox を通過するペアのうち折り線ペアの割合）:

| 立体 | bbox通過ペア | うち折り線ペア | 割合 |
|---|---|---|---|
| prism7 | 14,265 | 10,277 | **72.0%** |
| lshape | 43,198 | 22,645 | **52.4%** |
| stairs | 58,686 | 29,781 | **50.7%** |

折り線ペアを `is_valid_layout(polys, folded_pairs)` の第2引数で渡して

prism7 **2.84x**、lshape **2.15x**、stairs **1.94x**。

⚠️ 省略してよい根拠は「折り曲げの構成」であって「たまたま重ならない」ではない。

ならない。これは回帰テスト
`test_folded_pairs_skip_does_not_change_validity` で固定した

真偽が一致することを確認する）。前提が崩れればこのテストが落ちる。

### Cycle 12: `layout_tree` の平行移動項をスカラ化 — **採用（1.15x、ビット一致を証明）**

**動機**: めくれの投影ループは1面あたり numpy 呼び出しが約10回あり、
そのほとんどが「3要素の内積」という極小演算。ディスパッチ費用が支配的だった。

**事前検証**（`tools/check_small_dot_bits.py`）:

| 演算 | スカラ式とのビット一致 |
|---|---|
| 3要素内積 `a @ b` | **一致**（30万回で不一致 0） |
| 3x3 行列ベクトル `R @ a` | **不一致**（30万回中 209,449 回） |

つまり「内積」だけならスカラ化してよいが「行列ベクトル」は順序が変わる。
そこで平行移動の定数項 `float(shift @ u_x)` のみをスカラ式に置き換えた
（減算1 + 内積2 + `float()`2 の numpy 呼び出しを削減）。

**検証**: `tools/hash_layout_bits.py` で**全立体・全全域木**の座標を
SHA-256 でハッシュ化し、変更前後で完全一致することを確認（box / frustum4 /
prism5 / lshape / prism6 のすべてで一致）。

**結果（`layout_tree` 単体、同一セッションA/B）**: 約 **1.15x**
（prism7 146→128、lshape 133→117、stairs 159→138 µs/tree）。

**不採用にした案**: 投影全体をバッチ行列積（`einsum` で `(rot.T) @ U`）にすると
`tools/check_projection_bits.py` で prism5 / frustum4 が**全木で不一致**だった。
軸平行な立体（box / lshape）だけは偶然一致するが、一般には丸め順が変わるので却下。

### Cycle 13: 外接矩形の重なり面積による交差計算の省略 — **採用（2.3x）**

**アイデア**: 「交差面積は外接矩形の重なり面積を超えない」という自明な上界を使う。
bbox の重なり面積 `ox*oy` がしきい値 `TOL*(dx²+dy²)` 以下なら、交差面積も
しきい値以下と**確定**するので `intersection` を呼ぶまでもない。

```python
ox = min(ax1, bx1) - max(ax0, bx0)   # bbox 重なりの幅
oy = min(ay1, by1) - max(ay0, by0)   # 高さ
if ox * oy <= thresh:                # 交差面積 <= ox*oy <= thresh
    continue                         # 交差計算そのものを省略
```

**効く理由**: 辺や点で**接するだけ**のペア（`ox` か `oy` が 0）は交差面積が
厳密に 0 なので、ここで丸ごと落ちる。Cycle 11 の折り線ペアと違い、
これは**折り線以外の接触**（切り開いた辺どうしが展開図で隣り合う場合）も拾える。

**結果（lshape の `is_valid_layout`、同一セッションA/B）**:
Cycle 11 済みの状態から **0.532s → 0.230s（2.3x）**。
`tools/timing_parts.py` では stairs の `is_valid_layout` が 5.73s → 3.56s。

**正しさ**: 上界 `area <= ox*oy` は実数で厳密。しきい値は相対 1e-7 で
浮動ノイズ（相対 ~1e-16）より遥かに大きいので、境界での誤判定は起きない。
境界の両側を回帰テスト
`test_is_valid_layout_bbox_overlap_shortcut_boundary` で固定した。

### Cycle 14: 前計算の追加と判定ループの浮動小数スカラ化 — **採用（小さめ・確実）**

2 つの独立した小改善。

1. **`layout_tree` 内の面インデックス配列の前計算**: LinearRing を一括生成する
   `indices = np.repeat(np.arange(n_faces), counts)` は面の頂点数だけで決まり
   木に依存しないのに、木ごとに作っていた。`prepare_layout` に移して共有する。
2. **`is_valid_layout` の外接矩形を Python float に落とす**: 以前は
   `arr[i, 0]` のように numpy スカラを取り出して比較・演算していた。
   numpy スカラは1演算ごとにディスパッチ費用が乗るため、面数の2乗回る
   このループでは効く。`shapely.bounds(...).tolist()` で float にしてから使う
   （値は float64 のままでビット同一）。

**結果（同一セッションA/B）**: `is_valid_layout` は lshape で 0.228s → 0.201s
（**1.1x**）、stairs で 3.13s → 2.93s。`layout_tree` は stairs で約 **1.04x**。
どちらも控えめだが確実で、丸め演算を変えない。

### Cycle 15: `_distinct_counts` の in-place ソート — **採用（署名 約1.1x）**

**動機**: 署名バッチの中で「行内の異なる色数」を数える `_distinct_counts` が
署名フェーズの約2割を占める。中身は `np.sort(h, axis=1)` の1行。

**検証**（`tools/probe_wl_rounds.py` で1ラウンドの内訳を実測、(2048,10) uint64）:

| 部分 | 時間 |
|---|---|
| WL 更新（`h*A + h[:,nxt]*B + gather*C + tag`） | 138 us |
| 色数カウント `np.sort` | 164 us |
| 色数カウント `copy().sort(axis=1)` | **148 us** |
| 色数カウント（行ごと `np.unique`） | 5240 us |

`h.copy()` して in-place ソートするほうが1割速い。等しい要素は同値なので
安定性は無関係で、結果は**完全に同じ**。

**結果（同一セッションA/B）**: signatures 4.89s → 4.42s（**約1.1x**）。
分割（box / frustum4 の 96 クラス）と既知数は不変。

**重要**: `probe_wl_rounds.py` は同時に「ラウンド打ち切り案」を**却下**する根拠も
与えている。stairs では最初の7ラウンドがほぼ全行（30万行）を処理し、
大半の行は**8〜15ラウンド目で初めて**細分が止まる。ラウンド数を上限で打ち切ると
大量の行が個別化（Python の行ごと処理）に落ちて**遅くなる**ため、この案は採らない。

### Cycle 16: 投影の軸ベクトルを `u @ R` に — **採用（ビット一致・小さめ）**

投影ループは `axis_x = face_rot.T @ u_x`（型は `(3,3).T @ (3,)`）で軸を作る。
`u_x @ face_rot` と数学的に同じで、乱数 20万回で**ビット単位で一致**（不一致 0）、
かつ転置ビューを作らないぶん1割ほど速い（932 → 817 ns / 回）。

**結果**: `hash_layout_bits.py` が全立体で完全一致。prism7 の `layout_tree` も短縮。
1面あたり 2 回の改善なので効果は小さいが、丸めを変えないので採用。

### Cycle 17: 回転・平行移動の配列化と投影の軸バッチ — **採用（ビット一致）**

`layout_tree` の回転 `rot` / 平行移動 `off` を list ではなく最初から numpy 配列
（`(F,3,3)`, `(F,3)`）に貯め、投影の軸 `u @ rot[i]` を `einsum('b,fba->fa')` で、
平行移動の定数項 `(off - origin) @ u` を成分和で一括計算する。

- `tools/check_projection_axes_bits.py`: 軸は 2万回で不一致 0、**投影座標も不一致 0**。
- `hash_layout_bits.py` は全立体で完全一致。

孤立計測では投影が約 1.06x（中央値）。小さめだが丸めを一切変えない。

### Cycle 18: 投影そのものを全面バッチ化 — **採用（丸めは変わるが観測差なし）**

Cycle 12 では「行列ベクトルはバッチ行列積にできない」として見送った投影を、
**成分ごとの明示計算**（`P[:,0]*AX[:,0] + P[:,1]*AX[:,1] + P[:,2]*AX[:,2]`）で
全面バッチ化した。face 数ぶんあった GEMV 呼び出しが数回のベクトル演算に落ちる。

- **ビット一致はしない**: `tools/check_projection_batching.py` で、
  `(P*AX).sum(axis=1)` も明示左結合形も、GEMV と 20,000/20,000 で不一致。
  BLAS の GEMV カーネルと要素ごとの積和では積和順序（FMA の有無）が違うため。
- それでも採った根拠（**丸め順序は速度と引き換えにしてよい**、ただし
  **観測できる差がないこと**を条件にした）:
  - API golden（同値タイに敏感な prism4 を含む）が**無変更で通る**。
  - `tools/hash_metrics_rounded.py`: 全立体で指標 (9桁丸め) の多重集合が一致。
  - 既知の一意数・分割一致・全 277 テストが変わらない。
- 孤立計測の投影は約 2.0〜2.5x（1.61x / 3.44x / 2.58x、CPU 時間で 88→48us 級）。

| 立体 | box | frustum4 | prism5 | lshape | prism6 |
|---|---|---|---|---|---|
| 9桁丸め指標ハッシュ | 一致 | 一致 | 一致 | 一致 | 一致 |

### Cycle 19: WL 更新の in-place 化 — **採用（ビット一致・署名 約5%）**

`_batch_stabilize` の 1 ラウンドは 1 本の式で書くと `(rows, n_nodes)` の一時配列が
9 個できる。実サイズ（stairs で **2048 x 48** uint64 = 786 KB）では確保と
メモリ帯域が支配的で、更新 1 回が 1.3〜3.3ms（壁時計、負荷依存）に達する。

```
nh = h * A
t = h[:, nxt]; t *= B; nh += t
t2 = take_along_axis(h, partner_or_self, axis=1); t2 *= coef; nh += t2
nh += tag
```

一時配列が 9 個 → 3 個。uint64 の和は**順序で値が変わる**ので足す順序は元と同一。

- `tools/check_wl_update_inplace.py`: 2000 回で不一致 0。
- `hash_layout_bits.py` は Cycle 18 と完全一致（選ばれる木まで同一）。
- 孤立計測（CPU 時間、交互 A/B）で更新は約 **1.7x**。
- 署名フェーズ全体では希釈され、`tools/bench_signatures_cpu.py` で
  **約 5%**（4.80s → 4.55s、CPU 時間の最小値）。

⚠️ **計測手法の追加**: 外部負荷で壁時計が 5 倍振れる区間では、`time.process_time`
（プロセスが実際に使った CPU 時間）で交互 A/B すると判断できる。
`check_wl_update_inplace` の in-place 版は壁時計では「0.94x（遅い）」に見えたが、
CPU 時間では 1.7x 速かった。**壁時計だけでは逆の結論を出しかけた**。

## B.6 第2ラウンド（Cycle 20〜25）: バッチ化と計測手法の作り直し

Cycle 19 までで「1 本ずつのループを配列に置き換える」手はほぼ出し切っていた。
第2ラウンドは**窓（既定 2048 木）単位でのバッチ化**と、**測れない状態を直すこと**
から始まった。後半のサイクルは、最初に作った計測手法では差が見えなかったこと
（< 5% は外部負荷に埋もれる）を踏まえて、計測そのものを作り直してから進めている。

### Cycle 20: 窓単位のバッチ展開 `_layout_batch` — **採用（ビット一致）**

面数 10 程度では `layout_tree` は計算量ではなく **numpy 呼び出しの固定費**が
支配的（1 本あたり 50 回超、1 回あたり約 1.1us）。木の本数ぶん軸を 1 つ増やし、
窓内の全木をまとめて展開すれば同じ演算を数十回の呼び出しに畳める。

ビット一致の条件（`tools/check_layout_batch_bits.py`、204,633 レイアウトで不一致 0）:

- `np.matmul((B,3,3),(B,3,3))` は 1 本ずつの `(3,3)@(3,3)` と一致。
- 軸の `u @ rot` は `np.matmul(u, rot)` が per-tree の `einsum` と一致。
- **バッチ `einsum` は一致しない**（カーネルが変わる）。`matmul` を使う。
- `linearrings` は ring ごとに独立なので、座標を連結しても同じ ring になる。

`prepare_layout` に折り回転表（`fold_r_tab` / `fold_w_tab`）を持たせ、
`iter_unique_nets` は窓内の一意な木を集めてから一括展開し、**木の順序どおり**に
重なり判定して返す。

stairs の layout 5.3s → 0.88s、パイプライン 13.2s → 7.4s（CPU 時間）。

### Cycle 21: 色数を数え始めるラウンド `_WL_MIN_ROUNDS` — **採用（正しさの修正を含む）**

バッチ版の色は `A*h + B*h[nxt] + C*h[partner] + ...` という **uint64 の線形結合**
なので、早期のラウンドでは値が線形従属して衝突が残る。すると「分割が起きたのに
色数が変わらない」＝**見かけの安定**が起き、行が早すぎるタイミングで凍結する。

- 実測（`tools/probe_wl_collisions.py`）: lshape 8,100 行で 3 ラウンド目 66 行、
  4 ラウンド目 28 行、**5 ラウンド目以降は 0 行**。stairs は 3 ラウンド目で
  2,808/150,528 行。
- 旧実装はこれを `_individualize_refine` で拾い直していた（正しいが遅い）。

そこで 1〜5 ラウンド目は `_distinct_counts` を呼ばない。安定判定を「色数が増えなく
なったラウンド」から動かさないまま、偽の安定を最初から取り込まない。ついでに
その区間の色数計算（ほぼ全部が残るので捨て仕事）が丸ごと消える。

署名 5.44s → 4.66s、パイプライン A/B 8.219/8.234 vs 旧 8.750/9.422。

### Cycle 22: 正規形キーをビッグエンディアンのバイト列に — **採用**

キーを Python の tuple にしていたため、`.tolist()` で (2048,48) ぶんの Python int を
作る行がキー生成の大半を占めていた（実測 0.44s）。ソート済みの色列を
`astype(">u8").tobytes()` のバイト列にすると、辞書順が数値順と一致し固定幅の連結が
タプルの辞書順と一致するので、`min(自分, 鏡像)` の選び方まで tuple 版と同一。
個別化まで行った行は `_key_bytes`（符号 1 バイト + 絶対値 8 バイト = 9 バイト/色）。

署名 4.66s → 3.22s、パイプライン 1.16x（7.48s → 6.42/6.47s）。

### Cycle 23: WL ラウンドの作業バッファ再利用 + 平坦添字 gather — **採用（ビット一致）**

ラウンドごとに `(rows, n_nodes)` の一時配列を新規確保すると、初回書き込みの
ページフォルトだけで更新 1 回に数百 us 乗る（実測 (2048,48) で確保あり 1250us →
事前確保 469us）。出力バッファを 2 枚交互に使い（入力 `h` と別の実体にする必要が
ある）、接着相手の色は 2 次元 gather ではなく **平坦化した 1 次元 gather** で引く。

- 孤立計測（交互実行の最小値）で 1 ラウンドは 2.3〜4.0x。
- in-situ のペア計測で `_batch_stabilize` 9%、パイプライン 4.5%。
- ⚠️ 実装中に一度バグを出した: 行を間引いた後に**元の行オフセット**で平坦添字を
  作ってしまい `IndexError`。行オフセットを `keep` と同時に作り直して解決。

### Cycle 24: `is_valid_layout` の外接矩形段をバッチ前置フィルタに — **採用**

判定式（外接矩形の重なり → 和集合の対角を基準にした閾値 → `ox*oy` → 交差面積）は
そのままに、**窓の全ネットに numpy でまとめて適用**する `_valid_batch` を足した。
1 本ずつだと面数の 2 乗（面数 10 で 45）回る Python 二重ループと、ネットごとの
`shapely.bounds` / `.tolist()` の固定費が本体だった。

- 交差計算そのものは**ネットごとに逐次・早期終了**のまま。順序も式も同じなので
  呼ぶ `intersection` の回数も順序も一致し、判定はビット単位で同じ
  （stairs: 候補 124,039 ペアに対し交差 51,605 回、不一致 0）。
- 外接矩形は `_layout_batch` がポリゴン生成と同時に返す（GEOS 呼び出し 1 回）。
- ペア計測で stairs 1.08x、lshape 1.17x、prism7 1.21x、prism6 約1.1x。

### Cycle 25: 全色が別に達した行の色数を数えない — **採用（ビット一致・小）**

色数が `n_nodes` に達した行はもう細分できないので、次のラウンドの色数も必ず
`n_nodes`（＝同じ値）で done が確定する。数えるのをやめる（色数は `counts` の複製を
使う。全色別の行は新旧の色数が等しいのでそのまま流用できる）。

- 全色別の行は stairs で row-round の 12.6%、lshape で 15.8%。
- `_batch_stabilize` は細かいタイマで **6%**（ペア 6 ラウンドの最小値）。
- パイプライン全体では 2% 級で、計測の分解能の内側。

### 計測手法（このラウンドで確立したこと）— ここが第2ラウンドの主な成果

このマシンは外部負荷で **壁時計が最大 5 倍**振れる。さらに **`time.process_time`
にも刻みが約 15.6ms** あり、16ms 未満の呼び出しは 0 としか出ない。結果として:

- 別プロセスで順番に測る CPU 時間 A/B（`bench_pipeline_cpu.py`、交互・最小値）でも
  **5% 未満の差は判定できない**。Cycle 23 自身の変更がパイプラインで
  1.12x / 1.03x / 1.003x、`_batch_stabilize` で 1.058x / 1.046x と出て、
  「3x 速いはずの更新が効いていない」と誤読しかけた（実際は正しく効いていた）。
- **有効な手法**: HEAD の `fifth.py` を `git show` から取り出して**別モジュールとして
  import** し、**同一プロセス内で新旧を交互に**走らせて**ラウンドごとの比**を取る。
  負荷は両方に等しく乗るので比が残る。5 ラウンドの中央値で分解能は 2% 程度。
  奇数ラウンドで順序を入れ替えると「先に走ったほうが有利」という系統誤差も消える。
  - `tools/probe_ab_pipeline.py`（パイプライン全体、`_batch_stabilize` の累計つき）
  - `tools/probe_ab_stabilize.py`（関数 1 つ。16ms 未満の呼び出しは内側で繰り返す）
- 孤立マイクロベンチは**順序に強く依存**するので、交互（ラウンドロビン）にしないと
  信用できない。さらに**ランダムな添字で測った gather は実データより不利**に出る
  （実際の `partner_or_self` は構造的でキャッシュに乗る）。**in-situ のペア計測の
  数字を採用する**こと。

### 却下した案（Cycle 17〜25 で試したもの）

- **バッチ窓サイズの変更**（`tools/probe_window_size.py`）: 512/1024/2048/4096/8192 を
  比較して 2048 が最小（現行のまま）。小さい窓は固定費、大きい窓は初回ラウンドの
  行数で不利。
- **`np.take_along_axis` → 平坦 `np.take`**: (2048,48) ではほぼ差なし
  （714 → 648us）。ランダムアクセスで (2048,10) ほど効かないので不採用。
- **BFS の 2 つの行列積を拡大行列 1 回に統合**: `A @ [R|w]` は `A@R` と
  106,854/200,000 で不一致（GEMM は形で丸めが変わる）。不採用。
- **`shapely.bounds` の object 配列化を外す**: むしろ遅い（2.98 vs 2.71us）。現行のまま。

Cycle 20〜25 で試したもの:

- **窓サイズの変更**（`tools/probe_window_size.py`）: 512 / 2048 / 8192 / 32768 で
  出力は完全に同一（valid=5,714、sha256=`4783fafc81ea7e628a8ea453`）。時間は
  2048 が最小（8.61s 対 10.45 / 9.86 / 10.61）で **現行のまま**。
- **「面の面積の総和 > 外接矩形の面積」で不正を事前に弾く**: 有効な展開図では
  面が互いに重ならないのでこの不等式は必ず成り立つ（**確実に不正と言える**）。
  実測で有効なネットを 1 本も誤って弾かないことも確認したが、**弾けるのは
  不正の 3.7% だけ**（stairs 1,186/31,990、lshape 77/2,552）。閾値 1.0 の前後で
  比が 0.857（有効の最大）と 1.143（弾いた不正の最小）に分かれているものの、
  分布は大半が 1.0 以下。費用対効果が合わないので不採用
  （`tools/probe_area_filter.py`）。
- **交差計算の完全バッチ化**（`shapely.intersection` を候補全ペアに一括適用）:
  判定は**完全に一致**（不一致 0）だが stairs で **1.8x 遅い**。早期終了が
  GEOS 呼び出しの 58%（124,039 → 51,605）を削っているため、全ペアを計算すると
  負ける（`tools/probe_batched_intersection.py`）。
- **候補ペアの走査順の並べ替え**: 判定は「どれか 1 つでも重なれば不正」なので
  順序は自由。外接矩形の重なり面積 `ox*oy` の降順に並べても
  **交差計算の回数は 51,605 回のまま**（stairs）。素の添字昇順ですでに当たりの
  ペアから試している（`tools/probe_candidate_order.py`）。
- **接着相手の gather を `take_along_axis` のまま + バッファ再利用**: stairs では
  平坦添字版と同等（1.053x vs 1.058/1.046x）、lshape / prism6 ではむしろ遅い
  （1.4ms 級の差）。平坦添字版を採用。
- **交差面積の取り出し方**: `shapely.area(shapely.intersection(a,b))` は
  `.intersection(a,b).area` と雑音の範囲で同じ。`shapely.lib.intersection` は
  遅い（30.5us）。現行のまま。
- **列挙の triples 変種**（`probe_enum_variants`）: stairs 0.963（遅い）、
  prism7 1.214（速い）、lshape 1.000 → 雑音。不採用。
- **`_is_connected` のビットマスク化**（`tools/bench_is_connected.py`）:
  list 版 7.84ms に対しビットマスク 9.42ms。**現行のほうが速い**ので不採用。
- **`prune` で `partner_or_self` / `partner_coef` / `tag` を 1 本の配列にまとめる**:
  メモリ量は同じで、呼び出し回数だけが減る。`prune` は全体の 3.7%（stairs）で、
  削れるのはその一部なので見送り。

### 残る高速化の余地（Cycle 25 時点）

- **`_batch_stabilize`（stairs で約2.0s、パイプラインの約3割）**。内訳は
  更新 1.1s / 色数 0.35s / 間引き 0.24s / 初期化 0.25s。更新は
  **(2048,48) の配列を 1 ラウンドで 10 パス前後**触るのでメモリ帯域律速
  （実測 462〜544 ns/row-round）。パスを減らす以外に縮める手がなく、
  64bit の色を 32bit にすると衝突確率が実用にならない（1.8M 個で 2^-32 では不足）。
- **`is_valid_layout` の交差計算（stairs で約1.4s、うち GEOS 呼び出し 51,605 回）**。
  面数 10 のネットで約 1.37 回/本。候補の絞り込みはすでに厳しく（外接矩形と
  `ox*oy` の閾値）、早期終了も入っている。順序を変えても回数は減らない（実測）。
  交差を一括化すると 1.8x 遅くなる（早期終了を失うため）。
- **`_batch_canonical_keys` の周辺**（約0.8s）: 窓の木を numpy 配列にする
  `np.asarray` が 0.30s（36,864 個の Python int を 1 窓あたり詰め替える）、
  キーのソート + `astype(">u8")` + `tobytes()` が 0.28s、個別化 0.20s、接着 0.155s。
  いずれも構造（Python の全域木 → numpy）に由来する。
- **`enumerate_spanning_trees`（1.1s）**。1 本あたり約 7.6us。再帰の Python ループで、
  応用上はここが**最初に効いてくる**（1 本ずつ生成してから重複を潰している。
  列挙と同型判定を融合する手は Part B の (B) 系で検討した）。
- ただし**いずれも定数倍**であり、面数を増やすと全域木数が指数的に増える
  という構造的な壁は越えられない（Part B の本題）。14 面（cross = 43,804,800 本）は
  依然 15 分超で、実用の境界は 10〜12 面にある。
